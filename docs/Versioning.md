# eWorkHelper 版本号规范

## 1. 适用范围

eWorkHelper 统一使用本文定义的版本号规则。后续程序集版本、文件版本、测试构建、发布候选版本、正式 Release 及 UI 对外展示均应采用同一套规则，不得并行引入第二套版本格式。

本文只定义版本管理规范。实际调整项目版本号时，应在对应开发或发布任务中按本文执行，并同步更新相关项目元数据和发布文档。

## 2. 版本号格式

统一采用四段式：

```text
Major.Minor.Date.Revision
```

示例：

```text
1.2.260822.1
```

对外展示、日志记录、问题反馈和发布说明必须保留完整四段版本号，不得省略日期段或当日修订号。

## 3. 各字段含义

### Major：主版本号

发生以下任一情况时递增：

- 重大架构调整。
- 对现有使用方式、数据处理方式或部署方式产生重大兼容性变化。
- 进入新的主要产品阶段。

Major 递增不替代日期和修订号。新主版本仍必须记录实际生成日期，并从当日正确的 Revision 开始。

### Minor：功能版本号

发生以下情况时递增：

- 完成一组边界明确、可验收的新功能。
- 进入新的功能开发或交付阶段。

单个 Bug 修复、小范围交互调整、文案修正或不改变功能阶段的维护工作，不单独增加 Minor，而是通过新的 `Date.Revision` 区分。

Minor 递增时同样保留实际生成日期和当日修订号。

### Date：版本生成日期

- 固定采用 `yyMMdd` 格式。
- 日期必须是该版本实际生成的自然日期，不得使用计划日期、提交日期或任意占位日期代替。
- 示例：`260822` 表示 2026-08-22。

### Revision：当日修订号

- 每个自然日从 `1` 开始。
- 同一天再次生成内容不同的有效版本时，依次递增为 `2`、`3`……。
- 日期变化后，Revision 重新从 `1` 开始。
- 同一完整版本号只能对应唯一的一组构建内容；不得为不同二进制文件或不同源码状态重复使用同一版本号。

## 4. Major 与 Minor 的判定

版本调整前应先判断变更所属层级：

1. 若包含重大架构、兼容性或产品阶段变化，递增 Major。
2. 否则，若完成一组明确的新功能或进入新的功能阶段，递增 Minor。
3. 否则，Major 和 Minor 保持不变，仅根据实际生成日期及当日构建顺序更新 Date 和 Revision。

Major 或 Minor 是否递增应在开发记录或发布任务中说明理由，避免仅因日期变化或普通 Bug 修复而提升功能版本。

## 5. Date 与 Revision 生成规则

生成新版本时按以下顺序确定：

1. 确定本次变更是否需要递增 Major 或 Minor。
2. 使用本次实际生成日期生成六位 `Date`。
3. 查询该日期下已经生成的有效版本。
4. 当日没有既有版本时，Revision 使用 `1`；已有版本时，使用当前最大 Revision 加 `1`。
5. 将完整四段版本号写入需要更新的程序集和发布元数据，并确保各处一致。

版本号一旦用于可识别的测试包、发布候选包或正式发布包，就不得将相同版本号重新用于内容不同的构建。

## 6. 测试版本与发布版本

### 测试和发布候选版本

- 需要交付验证、问题定位或保留结果的测试构建必须分配完整四段版本号。
- 每次内容发生变化并重新生成有效测试构建时，都应使用新的 `Date.Revision`。
- 同一天的后续测试构建递增 Revision；跨天重新构建时使用新日期并将 Revision 重置为 `1`。

### 正式发布版本

- 正式发布应使用已经完成验证的构建所对应的完整版本号，确保测试结果和发布内容可追溯到同一构建。
- 如果发布前重新构建并导致产物内容变化，必须生成新的版本号；同日递增 Revision，跨日使用新 Date 并从 Revision `1` 开始。
- Release Notes、Git Tag、安装包元数据以及其他对外版本信息应与最终程序集完整版本号一致。
- 不得为了沿用原计划版本号而让内容不同的发布包复用已使用的完整版本号。

## 7. 示例

```text
1.2.260822.1
```

表示：

- 主版本阶段为 `1`。
- 功能版本阶段为 `2`。
- 该版本于 2026-08-22 生成。
- 这是当天第 1 个有效版本。

同一天修复问题后再次生成：

```text
1.2.260822.2
```

次日再次生成且 Major、Minor 不变：

```text
1.2.260823.1
```

若完成一组新功能并进入下一功能阶段：

```text
1.3.260823.2
```

## 8. .NET Framework 程序集元数据映射

`Date` 使用六位 `yyMMdd`，其数值可能超过 .NET Framework `System.Version` 单段允许的最大值 `65535`，因此不得将完整版本号直接写入只接受四个 16 位数值段的 `AssemblyVersion` 或 `AssemblyFileVersion`，否则会导致编译失败或产生无效元数据。

项目采用以下唯一映射规则：

- `AssemblyInformationalVersion` 保存并对外代表完整的 `Major.Minor.Date.Revision` 产品版本号。
- Release Notes、Git Tag、安装包展示、问题反馈和 UI 均使用 `AssemblyInformationalVersion` 中的完整版本号。
- `AssemblyVersion` 和 `AssemblyFileVersion` 仅作为 CLR/VSTO 兼容性字段，使用合法且稳定的数值版本；它们不构成第二套产品版本号，也不得用于对外展示。
- 实际升级版本时必须更新 `AssemblyInformationalVersion`；仅在确有 CLR 绑定或兼容性需要时，才单独调整数值兼容字段并记录原因。

## 9. UI 获取版本号原则

- 禁止在 Ribbon、窗体、关于页面、提示文本或其他 UI 中硬编码版本号。
- 需要展示版本时，必须从当前运行程序集的 `AssemblyInformationalVersion` 动态读取。
- UI 必须展示完整四段版本号，不得截断 Date 或 Revision。
- UI 展示值应与程序集实际版本保持一致，不得另行维护显示专用版本常量或配置。

## 10. 执行要求

- 后续实际版本调整必须按照本文确定 Major、Minor、Date 和 Revision。
- 版本变更应同步记录变更原因、生成日期、当日修订序号及验证/发布用途。
- 本规范建立时不修改项目当前实际版本号；首次按新规范调整版本号应由后续独立任务完成。
